## Requirements
### Requirement: Server-rendered SvelteKit application

The PerchPub web frontend SHALL be a SvelteKit application running under `adapter-node` that server-renders its pages, replacing the prior static React SPA. It SHALL be served as a Node process on port `3000` behind the Traefik router for the public apex host (`${DOMAIN}`, with `www`→apex redirect), and SHALL reach the backend over the internal network (`INTERNAL_API_URL`, e.g. `http://backend:8000`) for all server-side data access, making the web app same-origin from the browser's perspective.

#### Scenario: a public page is server-rendered
- **WHEN** an anonymous client requests a public page
- **THEN** the response HTML already contains the page's server-rendered content (not an empty client-only shell), produced by a SvelteKit server `load`

#### Scenario: the browser never calls the backend cross-origin
- **WHEN** the rendered app fetches application data
- **THEN** requests go to the same origin as the page (the SvelteKit server or its `/api`/`/media` routes), and no browser request is made directly to the `api.*` origin

### Requirement: BFF cookie-session authentication

Authentication SHALL use a backend-for-frontend model: a successful login SHALL set an `httpOnly`, `Secure`, `SameSite=Lax` cookie (`pp_session`) holding the backend JWT, and the SvelteKit server SHALL forward that JWT as an `Authorization: Bearer` header to the backend on the user's behalf. The JWT SHALL NOT be exposed to client-side JavaScript. A backend `401` (expired or invalid token) SHALL clear the cookie. Logout SHALL clear the cookie.

#### Scenario: login establishes a session cookie
- **WHEN** a user submits valid credentials to the login form action
- **THEN** the backend `/login/access-token` call succeeds, the server sets an httpOnly `pp_session` cookie, and the user is redirected to the post-login target

#### Scenario: the JWT is never sent to the browser
- **WHEN** a logged-in user loads any page
- **THEN** the JWT appears only in the httpOnly cookie and in server-to-backend requests, and is not present in any client-readable response body, header, or client storage

#### Scenario: an expired session is cleared
- **WHEN** a request carries a `pp_session` cookie whose JWT the backend rejects with `401`
- **THEN** the server clears the `pp_session` cookie for that response

### Requirement: Public and authenticated routing zones with server-side guards

The app SHALL expose a public zone reachable without authentication and an authenticated zone protected by a server-side guard. The authenticated zone's guard SHALL run during server-side `load` and SHALL redirect unauthenticated requests to the login route. The public zone SHALL NOT require authentication.

#### Scenario: unauthenticated access to the authed zone is redirected
- **WHEN** a request without a valid session targets a route in the authenticated zone
- **THEN** the server redirects it to the login route before rendering protected content

#### Scenario: the public zone is reachable anonymously
- **WHEN** an anonymous request targets a public-zone route
- **THEN** the page renders without any authentication redirect

### Requirement: Optional authentication on public pages

Public-zone server `load` SHALL forward the session bearer to the backend only when a `pp_session` cookie is present, so that endpoints with optional-user visibility return the enriched (owner) view for logged-in users and the public view otherwise. A cookie-expiry `401` originating from a public page SHALL NOT force a logout redirect.

#### Scenario: an owner sees private resources on a public page
- **WHEN** a logged-in owner loads a public page backed by an optional-user endpoint
- **THEN** the server forwards the bearer and the page includes resources visible only to that owner

#### Scenario: an anonymous visitor sees only public resources
- **WHEN** an anonymous visitor loads the same public page
- **THEN** the server sends no bearer and the page includes only the publicly visible resources

### Requirement: Generated, typed API client

The frontend SHALL consume the backend exclusively through a typed client generated from the backend's OpenAPI schema (`openapi-typescript` + `openapi-fetch`), regenerated by a committed script. Endpoint URLs SHALL NOT be hand-written in application code.

#### Scenario: API access uses the generated client
- **WHEN** application code calls a backend endpoint
- **THEN** it does so through the generated typed client, and the call fails type-checking if the path or payload does not match the generated schema

#### Scenario: the client is regenerated from the live backend
- **WHEN** the generate-client script is run against the backend
- **THEN** it produces types for the current backend resources (including Station, Observation, Species, ClassifyTask, Enrollment, Users)

### Requirement: First-station onboarding on the dashboard

The authenticated dashboard SHALL be onboarding-aware: its server `load` SHALL determine how many stations the current user owns, and when the user owns **zero** stations the dashboard SHALL lead with a prominent "set up your first station" call to action that routes to the station-setup wizard. When the user owns **one or more** stations the dashboard SHALL NOT show that onboarding call to action. This onboarding recommendation SHALL be the standing post-signup next step until the user owns at least one station.

#### Scenario: a user with no stations sees the setup call to action

- **WHEN** a logged-in user who owns zero stations loads the dashboard
- **THEN** the dashboard leads with a prominent "set up your first station" action that links to the station-setup wizard

#### Scenario: a user with a station sees the normal dashboard

- **WHEN** a logged-in user who owns at least one station loads the dashboard
- **THEN** the dashboard does not show the first-station onboarding call to action

### Requirement: Station setup is not a top-level navigation destination

The authenticated app shell's primary navigation SHALL NOT present station setup / device enrollment as a standalone top-level destination. Station setup SHALL be reached from the dashboard's first-station onboarding call to action and from the station list's secondary "Add station" action (see `station-management`). The primary navigation SHALL retain Dashboard, the station list ("My stations"), and Account (plus the superuser Admin section).

#### Scenario: the sidebar has no standalone enroll destination

- **WHEN** a logged-in user views the authenticated app shell
- **THEN** the primary navigation shows Dashboard, My stations, and Account, and shows no standalone "Enroll device" navigation item

#### Scenario: station setup remains reachable without a nav item

- **WHEN** a logged-in user wants to set up a station
- **THEN** they can reach the station-setup wizard from the dashboard onboarding call to action or the station list's "Add station" action

### Requirement: The station-setup wizard offers a defer-to-later escape

The station-setup wizard SHALL provide a "do it later" escape that leaves setup and returns the user to the dashboard, where the first-station onboarding call to action continues to recommend setup until a station exists. Deferring SHALL NOT create a station and SHALL NOT prevent later setup.

#### Scenario: a user defers first-station setup

- **WHEN** a logged-in user who owns no stations opens the setup wizard and chooses "do it later"
- **THEN** no station is created, the user is returned to the dashboard, and the dashboard still shows the first-station onboarding call to action
